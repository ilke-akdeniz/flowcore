# Decision Log

Design decisions for FlowCore, with the alternatives weighed and the reasoning that settled each one.
This log records _why_ the system is the way it is; `docs/system-design.md` records _what_ it is.

Entries are append-only.
A later decision that reverses an earlier one gets its own entry and notes what it supersedes, rather than editing the original.

Decisions 1–14 were settled together during the config-side slice of iteration 1 (migrations plus the definition-side repository layer).

---

## 1. Single root package, not `internal/`

**Context.**
The repository layer needed a home.
The initial briefing placed it under `internal/workflow/`, which Go makes unimportable by any other module — meaning the slice would ship nothing a client could call, and the public surface would be designed a slice later, after the repository types had already set.

**Options.**
Repositories in `internal/`, no public API this slice.
Repositories in `internal/` plus a thin public façade at the root.
Everything public in a `config` package, no `internal/`.
One package at the module root, privacy by identifier case (surfaced during discussion, not in the original three).

**Decision.**
One package `flowcore` at the module root.
The store is unexported (lowercase) in its own files; the exported types and `Definitions` sit alongside it.
`internal/` is deleted.

**Why.**
In Go, privacy comes from identifier case, not directory.
A lowercase type in the root package is exactly as unreachable to a client as one under `internal/`.
`internal/` solves a narrower problem — hiding a package when several packages must call each other by exported name — which a single-package module doesn't have.
Splitting store from façade across a package boundary would force two representations of each entity and a mapping layer between them: the exact duplication-and-drift the owner was worried about.
One package makes that structurally impossible — there is one `StepDefinition` type, read from Postgres by the store and handed to the client by the façade.
The "internal types calcify" fear was also overstated: nothing is published, there are no tags, and a v0 module carries no compatibility promise, so exported identifiers can be renamed freely until v1.

**Consequence.**
Discipline moves from the compiler to the author: nothing stops code reaching into the store directly, since there's no package wall.
For a library this size with one author and a reviewer, that's cheaper than the mapping tax a wall would charge.
`internal/` can be introduced later if a second package genuinely needs to share machinery.

## 2. UUIDv7 ids, application-generated

**Context.**
Every table needs a primary key strategy, and the choice is the most expensive in the slice to reverse — converting bigint↔UUID later is a full schema migration touching every table and FK.

**Options.**
bigint identity (sequence-generated by the DB).
UUIDv7 generated in Go before insert.

**Decision.**
UUIDv7, application-generated via `github.com/google/uuid`, `uuid` columns, no DB default.
Ids are exported on the types so a client may supply its own; the library fills any zero-value id.

**Why.**
Performance is not the deciding factor — config tables hold tens to hundreds of rows, so index size is noise.
Three things decide it.
Aggregate-create ergonomics: with app-generated ids the repository assigns every step id in Go before touching the DB, so actions can reference real step ids immediately and the whole aggregate is a flat sequence of plain inserts — no `RETURNING`, no id-map, no second pass.
Portability: a client stores the workflow-definition id in their own tables, and a sequence-derived id differs across dev/staging/prod, so the same logical definition can't be referenced by hardcoded id across environments; a client-suppliable UUID makes "ensure definition 0192… exists" an idempotent seed that's identical everywhere.
Boringness cuts slightly toward UUID too — no `RETURNING` dance.

**Consequence.**
Reversing this is a full-schema migration, which is why it was settled early.
The exported-id + library-fills-zero-value shape enables the idempotent-seed pattern.

## 3. Action-to-next-step wiring: flat structs with explicit ids

**Context.**
At authoring time a Dev needs to say "approve on manager review leads to director review" — but at the moment they describe it, the target step may not have an id yet.
UUIDv7-in-Go settles who generates ids but not how the input expresses the reference.

**Options.**
A — flat structs, Dev generates step ids explicitly, actions carry `*uuid.UUID` next-step pointers.
B — a builder on top that returns handles and wires by reference, emitting the flat structs underneath.
C — local string keys resolved to ids at save time.
D — Go pointer wiring (`Action{NextStep: dir}`), making the struct a cyclic graph.

**Decision.**
A now; B available later as a purely additive convenience.
`NextStepID` is `*uuid.UUID`, nil meaning terminal.
Create takes the aggregate by value and returns the stored aggregate, filling any zero id into a deep copy so the caller's structs aren't mutated.

**Why.**
A is the only option where the write model and the read model are the same flat struct, which keeps the SQL and the tests boring.
C reintroduces the key→id map that app-generated ids just eliminated, plus an "unknown key" failure mode, and diverges write shape from read shape.
D poisons everything downstream — a cyclic struct can't be JSON-serialized by a client admin page, read-back has to rehydrate pointers, and test assertions loop.
B isn't foreclosed by A: a builder is pure client-side sugar that emits the same structs and touches no schema, so it can be added if authoring proves painful — which matches the design rule of building the right shape when the need actually arrives.

**Consequence.**
Typed `*uuid.UUID` nil-means-terminal aligns with the nullable DB column and is harder to set by accident than a `uuid.Nil` sentinel.

## 4. Same-definition integrity via composite foreign keys

**Context.**
Multiple definitions live in one database.
A plain FK on a step's status column only checks that the status _exists_ — it happily accepts a status belonging to a different definition, producing a definition that references another's rows.
The rule needed is "exists _and_ belongs to my definition," which a single-column FK can't express.

**Options.**
Composite FKs that include `workflow_definition_id` in the reference.
Application-level validation in the repository.

**Decision.**
Composite FKs.
Each parent (statuses, steps) carries a redundant `unique (workflow_definition_id, id)` to serve as the FK target; `action_definition` carries a denormalized `workflow_definition_id` so its FKs have a column to match on.

**Why.**
The composite FK checks the _pair_ (definition, status) against the parent, so a cross-definition reference finds no matching pair and is rejected.
It composes with nullable terminal actions for free — Postgres `MATCH SIMPLE` skips the check when the referencing column is null, so a terminal action's null next-step simply doesn't fire the FK.
Forward references need no deferral, because ids are generated in Go and the aggregate inserts statuses, then steps, then actions in order.
And it covers paths app-validation can't reach without tedium: every granular mutation, plus a client's admin tooling, plus a DBA in psql, would each need a same-definition SELECT forever; the FK is written once and holds for all of them — which matters most because this schema lands in databases the library doesn't control.
The denormalized `workflow_definition_id` on actions can't lie: the FK to its owning step checks it, so an action can't claim a definition its step doesn't share.

**Consequence.**
One denormalized column and two redundant uniques, each explainable in a one-line SQL comment.
This does not make the graph _valid_ — an action can still point at its own step, and unreachable steps are still allowed; that's deliberate and stays deliberate (no loop detection).

## 5. `ON DELETE NO ACTION` on the two reference FKs

**Context.**
Parent links cascade uncontroversially (delete a definition, its statuses/steps/actions go).
The two _reference_ FKs — a step's status, an action's next step — need a delete behavior chosen deliberately.

**Options.**
`SET NULL`, `CASCADE`, `RESTRICT`, `NO ACTION` on the reference FKs.

**Decision.**
`ON DELETE NO ACTION`, written explicitly, on both reference FKs.

**Why.**
`SET NULL` on next-step silently converts "approve routes to director" into "approve ends the workflow" — the definition still validates and quietly does the wrong thing.
`CASCADE` on next-step means deleting one step silently deletes actions belonging to _other_ steps.
`RESTRICT` and `NO ACTION` are behaviorally identical here, both blocking the delete until the referring rows are repointed or removed; `NO ACTION` wins only because it can later be marked `DEFERRABLE` if some bulk-rewire ever wants to tear down and rebuild a graph in one transaction, whereas `RESTRICT` can never be deferred — strictly smaller with no compensating benefit.
Written explicitly rather than by default so a reader sees it was a decision.

**Consequence.**
Deleting a referenced step returns a raw FK violation, which the repository must translate into something actionable (see decision 13).

## 6. Entry step via nullable self-referential FK

**Context.**
Nothing in the original State model said which step a workflow starts on — a gap, since the Engine needs it and it's a definition-side fact.
The natural fix creates a circular FK between `workflow_definition` and `step_definition`.

**Options.**
A — `workflow_definition.initial_step_definition_id`, nullable, with a composite FK into the same definition's steps.
B — a `position` ordinal, entry = lowest.
C — an `is_initial` boolean with a partial unique index.
D — derive it as the step no action points at.

**Decision.**
A.
Nullable column, set by a trailing UPDATE inside the aggregate transaction.
The circular-FK behavior was probed against Postgres: config-wide delete works despite the cycle, deleting the entry step is blocked, deleting a non-entry step is allowed, cross-definition entry steps are rejected, a null-entry definition is representable.

**Why.**
B models a directed graph as a sequence — it invites "next = position + 1" reasoning the action-routing model rejects, and can't represent branching.
C degrades on the operations that matter: changing the entry step is two order-sensitive UPDATEs, and deleting the entry step succeeds silently, leaving an unstartable definition — where A's FK makes that same delete fail loudly.
D breaks on cycles (no such step) and on multiple unreachable steps (two such steps).
Nullable is deliberate: a `NOT NULL` column would make the definition row un-insertable before its steps exist, forcing a deferrable FK; nullable plus one trailing UPDATE is more boring.

**Consequence.**
"Definition must have an entry step" is enforced by the aggregate create, not the schema; the Engine must fail clearly at start if it's null.
Aggregate insert order: definition (entry null) → statuses → steps → actions → UPDATE the entry-step id.
This added a field to the State section.

## 7. Terminal status carried on the terminating action

**Context.**
The doc's own example statuses include "approved" and "rejected," but every status hung off a step, and a finished run has no current step — so "approved"/"rejected" were unreachable.
Those are outcomes of a decision, not descriptions of a stage.

**Options.**
1 — the terminating action carries a nullable terminal status, with a CHECK that exactly one of next-step / terminal-status is set.
2 — model terminal statuses as real steps with no actions.
Defer the column to the Engine slice.

**Decision.**
Option 1.
`action_definition` gains a nullable `terminal_workflow_status_definition_id` and an XOR CHECK against `next_step_definition_id`.

**Why.**
Option 2 makes `step_definition` mean two incompatible things — everything a step carries (assignee, actions, completedBy, subjectVersionToken) is meaningless on a terminal marker, and the Engine would later materialize a Step instance nobody can act on, forcing the worklist to special-case "steps that aren't work."
That pays in Engine complexity to avoid one nullable column and one CHECK.
On the speculation question: without this column a Dev literally cannot express "reject ends the run as rejected," so the definition entity is incomplete on its own terms — not merely unprepared for a future feature — which is why building it now isn't speculative structure.
A single "completed status" on the definition was rejected as too coarse to distinguish approved from rejected.

**Consequence.**
The Workflow invariant changed: status reflects the current step's status while running, or the terminating action's status once complete.

## 8. Dedicated `flowcore` Postgres schema, plain names, schema-qualified queries

**Context.**
The library's tables land in a database it doesn't own, alongside tables it's never heard of.
`workflow_config` is a generic enough name that a collision with a client table is a live risk, and the failure mode is a migration that won't apply into an existing production database.

**Options.**
A — `public`, plain names.
B — `public`, prefixed names (`flowcore_workflow_definition`).
C — a dedicated `flowcore` schema, plain names.
D — configurable schema name.

**Decision.**
C.
Every query is schema-qualified in Go (`from flowcore.…`); the library never relies on `search_path`.
goose's version table is `flowcore_goose_db_version`, unqualified.

**Why.**
C is collision-proof by construction and lets a client grant, back up, inspect, or drop the library's storage as a unit.
Schema-qualifying in Go costs a few characters per query and removes an entire class of environment-dependent bug, since the client owns the pool and may set `search_path` to anything.
D was rejected because goose plain-SQL files don't template, and it adds a knob to every query path.
The version-table name is not cosmetic: a probe established that goose can't bootstrap its version table into a schema the migrations themselves create (it tries to create the table before the schema exists), so the version table lives in the default schema — and if it used goose's default name while the client also uses goose, the two migration histories would share one table and corrupt each other's state.

**Consequence.**
Migration 001 does `create schema if not exists flowcore`, needing CREATE privilege on the database — worth a README line.
The pinned `-table flowcore_goose_db_version` invocation must always be used, so it's wired into a Makefile target.

## 9. Uniqueness constraints: scoped, case-insensitive, length-capped

**Context.**
Duplicate names within a definition are authoring bugs — two "approved" statuses, or two "approve" buttons on one step, make a human-facing UI a lie, since the Caller selects by id but a person picks by name.
The contentious sub-question was whether `workflow_definition.name` is globally unique.

**Options.**
Global uniqueness on definition name, or none.
Case-sensitive vs case-insensitive scoped uniqueness.
A length cap vs none.

**Decision.**
No uniqueness on `workflow_definition.name`.
Case-insensitive scoped uniqueness on statuses `(workflow_definition_id, lower(name))`, steps `(workflow_definition_id, lower(name))`, actions `(step_definition_id, lower(name))`, as explicitly-named functional unique indexes.
`check (char_length(name) between 1 and 200)` on all four name columns.
`assignee_id`: nullable text, no FK, no CHECK, nothing.

**Why.**
Global definition-name uniqueness would break a multi-tenant client whose customers each want their own "Expense Approval" — the library would be imposing a policy on the client's data model, the same overreach as interpreting `assignee_id`, and the library never looks a definition up by name anyway (start takes an id).
Case-insensitive on _all three_, not just actions: "Approve"/"approve" is the same authoring bug at every level, and mixed sensitivity across sibling tables is a trap.
Indexes are explicitly named because a functional unique index isn't a table constraint and won't show in `pg_constraint` under an inferable name — the error mapper (decision 13) needs a stable `ConstraintName` to key on.
The length cap replaces a bare non-empty check and has a real reason beyond hygiene: names sit inside btree unique indexes, whose entries cap at ~2700 bytes, so an unbounded name fails at insert with an opaque index-internal error; the cap turns that into a clean, explainable violation, and 200 chars (~800 bytes worst-case UTF-8) is past any honest label.
Step-name uniqueness is kept despite branching graphs legitimately wanting "Manager Review" on two paths — because Get Current Step and the worklist are human-facing and identical names make both ambiguous, and it's the reversible direction (dropping a unique constraint later is trivial; adding one after clients hold duplicate data is not).

**Consequence.**
A functional index doesn't appear in `pg_constraint`, so the explicit names are load-bearing for error mapping, not cosmetic.
The cap permits whitespace-only names (`'   '`); that's treated as the client's presentation concern, not the schema's.

## 10. Private `querier` interface + one transaction idiom

**Context.**
The aggregate create must run every insert in one transaction; granular CRUD each run a single statement and should compose into a caller's transaction later (the Engine will want to read a definition inside its start transaction).
Those pull opposite directions if methods bind to a concrete type.

**Options.**
A private `querier` interface capturing `Exec`/`Query`/`QueryRow`, satisfied by both `*pgxpool.Pool` and `pgx.Tx`.
Concrete `*pgxpool.Pool` everywhere.
An exported interface.

**Decision.**
A private, unexported `querier` interface.
The exported surface takes `*pgxpool.Pool` at construction (`NewDefinitions(pool)`); the querier is internal plumbing beneath.
Transaction idiom at every site: `Begin`, immediate `defer func() { _ = tx.Rollback(ctx) }()`, `Commit` at the end — not per-branch rollbacks, not `pgx.BeginFunc`.

**Why.**
Concrete `*pgxpool.Pool` everywhere would force the aggregate create to duplicate every insert helper (pool version and tx version) or reach for raw batching.
An exported interface would be a public commitment to a shape pgx defines, so a pgx v6 signature change would trap the library between their break and its promise; private means free resignaturing.
Begin is deliberately left out of the interface so a helper _cannot_ start its own transaction — transaction control lives in exactly one place.
The deferred-rollback idiom was chosen over `BeginFunc` because it's the more prevalent, more idiomatic pattern in production Go/Postgres — it's what `database/sql` taught, it predates pgx, and it keeps return values on the normal return path rather than through a captured closure variable.
The post-commit rollback returning `pgx.ErrTxClosed` is expected and discarded; writing it once per site is what guarantees no leaked pooled connection on any error path.

**Consequence.**
A client holding a `Definitions` can't compose its reads into its own transaction — the Engine can, only because it lives in the same package and calls the unexported helpers directly.
If a rollback ever runs on an already-cancelled context it can't reach the server; pgxpool self-heals by discarding the connection, and the fix if it ever shows as churn is `context.WithoutCancel` — not pre-empted now.

## 11. Free functions over a store, one `Definitions` façade, definition-side CRUD built in full

**Context.**
Two coupled questions: the storage-layer shape, and how much of the granular CRUD surface to build this slice.
The owner comes from an OO/ActiveRecord background and wanted to know where business logic would live if the storage layer were free functions.

**Options.**
Storage: free functions taking `(ctx, querier, args)` vs per-entity store structs.
Surface: one façade vs a repository per entity.
Scope: build only what tests exercise vs the full CRUD surface.

**Decision.**
Free functions, one file per entity, unexported.
One exported `Definitions` façade owning transactions.
Full definition-side CRUD this slice — Create, Get, Delete, plus Add/Update/Delete for step, status, action.

**Why.**
The store helpers hold no state, so a struct would only wrap the querier that's already passed explicitly per call — ceremony.
Business logic isn't homeless under free functions: in Go it goes on the types (methods on `StepDefinition`) and in the façade (cross-entity invariants, transactions), while the store holds only SQL — DDD-with-repositories, not an anemic model, and most of this slice's rules are already in the schema (composite FKs, CHECKs, unique indexes) rather than in code.
Four repository objects would force a Dev to assemble their own cross-entity transaction, which is exactly the atomicity guarantee the library owns.
On scope: completing the obvious CRUD on entities that already exist is not speculation — it's finishing the library.
Applying the no-speculative-structure rule to `UpdateStep` was a category error; that rule governs schema and abstraction built for absent features (a `tenant_id`, a versioning table, a `canComplete` hook), not API completeness.

**Consequence.**
This prompted a clarifying edit to the no-speculative-structure rule in `CLAUDE.md` and the project instructions, distinguishing schema/abstraction speculation (defer) from finishing operations on existing entities (build), with a guard that "we'll need it eventually" is not a licence to build now.
`assignee_id` reassignment stays deferred — it's an instance-side mutation belonging to the Engine, with no definition-side table to act on.

## 12. Deep Get under repeatable read; Create the only tree-write

**Context.**
Two sub-questions: how deep Get returns, and the read/write mechanics of a four-level aggregate.

**Options.**
Get depth: shallow vs fully-loaded tree.
Read mechanics: one four-table join vs four sequential queries.
Consistency: a comment noting the torn-read risk vs a repeatable-read wrapper now.

**Decision.**
Get is always deep — the whole definition tree.
Four sequential queries assembled with map group-bys in Go, run inside a repeatable-read transaction.

**Why.**
A deep Get is the only shape consistent with the atomicity invariant — a reader sees the whole definition or none of it; a half-populated tree reintroduces the "under construction" view the invariant bans.
Four queries over one join because a four-table join fans out (5 steps × 3 actions = 15 rows to dedupe) and left-joins for empty sets get fiddly, while four queries each map cleanly to a slice.
The repeatable-read wrapper is taken _now_, not deferred as concurrency work, because it's this read's own correctness condition: four separate queries on the pool can straddle a concurrent edit and tear, and the snapshot guarantee is what the atomicity invariant requires — it introduces no locking decision and doesn't touch the deferred completion-path concurrency mechanism.

**Consequence.**
The justification is kept local to Get; it's not precedent for building other concurrency machinery this slice.
The completion-path locking mechanism stays deferred until that path is written.

## 13. Error taxonomy: typed+sentinel hybrid, central mapper split by operation intent

**Context.**
The slice deliberately manufactures a rich set of DB rejections — named unique indexes, composite FKs, the XOR CHECK, the referenced-delete block, the length CHECK, plus not-found.
Raw `pgconn.PgError` with SQLSTATEs leaves a Dev unable to tell a duplicate name from a cross-definition reference from a blocked delete.

**Options.**
Sentinel errors vs typed errors (settled as a hybrid).
Granularity by failure kind vs by entity.
Central mapper vs inline per call site.

**Decision.**
Typed errors that each wrap a sentinel (so both `errors.Is` and `errors.As` work), granular by failure kind with entity as a field, mapped centrally.
The taxonomy: `ErrNotFound{entity, id}`, `DuplicateNameError{Entity, Name}`, `CrossDefinitionError{}`, `ReferencedError{Entity, ID}`, `InvalidActionError{}`, `InvalidNameError{}`.

**Correction, mid-decision.**
The first cut keyed the mapper on SQLSTATE + `ConstraintName` alone.
A probe against Postgres overturned that: a referencing insert (cross-definition) and a referenced delete fire on the _same_ FK with byte-identical structured fields — same code, same constraint, same `TableName` (Postgres reports the constraint-owning table on both sides).
Only the human-readable message prose differs, which is locale-dependent and unusable.
So the mapper must be keyed by _operation intent_ as well: the same constraint yields `CrossDefinitionError` on a write path and `ReferencedError` on a delete path.
The probe also surfaced that referenced-deletes cover statuses, not just steps (`DeleteStatus` on an in-use status blocks on a `NOT NULL` FK), which is why `StepReferencedError{StepID}` was generalized to `ReferencedError{Entity, ID}`.

**Why.**
Detail matters because these are authoring errors a Dev's admin UI will display, not just branch on.
Granularity by failure kind, not table, keeps the taxonomy at ~6 types instead of ~15 and matches "map to the semantic violation, entity is a field."
A central mapper is the one place that knows constraint names, so a renamed index is a one-line fix — and it's the seam the Engine will reuse for its own concurrency errors.
Two intent wrappers (`mapWriteErr`, `mapDeleteErr`) were chosen over a single mapper with an op argument, because an op argument lets any call site pass the wrong op, while the wrapper makes intent implicit in which function the method calls; the delete wrapper is also the natural place to stamp the entity/id the raw error doesn't carry.

**Consequence.**
Every constraint the mapper switches on — unique indexes, composite FKs, CHECKs — must be explicitly named in the migrations, or the mapping collapses distinct failures.
`ErrNotFound` comes through a different entry path (`pgx.ErrNoRows` / zero-rows-affected), not the SQLSTATE switch.
The constraint-mapping test must provoke the two-sided constraints from _both_ sides, or a wiring mistake in one wrapper passes CI silently.
Scope line held: no error type without a DB signal that actually produces it this slice.

## 14. Test isolation by truncate; schema via pre-migrated DB

**Context.**
Two mechanical questions: how each test leaves the DB clean, and how the schema arrives given goose is kept out of `go.mod`.

**Options.**
Cleanup: transaction-rollback per test vs truncate-between-tests vs fresh schema per test.
Schema: assume a pre-migrated DB (Makefile wires migrate + test) vs `TestMain` shells out to the goose CLI.

**Decision.**
Truncate in setup (not teardown), tests serial, shared pool.
Pre-migrated DB: `TestMain` connects and sanity-checks the schema; a Makefile wires `migrate-test` (with the pinned `-table` invocation) and `test` into one command.
Dedicated `flowcore_test` database via `FLOWCORE_TEST_DSN`; `t.Skip` (not fail) when no DB is reachable.

**Why.**
Rollback-isolation is impossible here and was rejected on a hard constraint: `Definitions` holds a pool and `Create` calls `pool.Begin()` on its _own_ connection, so a test's outer transaction on a different connection can't roll back `Create`'s real commit.
Forcing it to work would mean constructing `Definitions` over a single test-controlled connection — reintroducing the test-only public surface decision 10 avoided — and worse, it would mean the atomicity invariant is never actually tested, since you can't verify a real commit you've neutered inside an outer rollback.
Truncate in setup rather than teardown so a failed test leaves its rows for `psql` inspection.
Pre-migrated over shelling out keeps `TestMain` free of `PATH` assumptions and process-spawning; the Makefile hides the two-step nature from daily use.
A dedicated test DB keeps truncation from wiping the dev database; `t.Skip` keeps `go test ./...` from hard-failing on a machine without Postgres.

**Consequence.**
Serial execution is a _designed_ correctness condition, not incidental: a shared-pool truncate strategy corrupts under concurrency, so all DB-touching tests live in one package and none calls `t.Parallel()`.
If the suite ever spreads across packages, `go test ./...`'s cross-package concurrency needs `-p 1` or a shared lock.
The existing pgx smoke test (which `t.Fatal`s) is deleted once real tests land, per its own TODO.
